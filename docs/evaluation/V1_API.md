# RagBot Evaluation V1 API

Base path: `/api/v1/evaluation`

All endpoints reuse the existing RagBot login. The frontend submits the same username/password request as the existing application to `POST /api/login`; successful authentication establishes the existing process-local authenticated user for the integrated evaluation control plane. No evaluation token, evaluation user table, or alternate password storage exists.

The current RagBot login does not issue a cookie or bearer token. Authentication must therefore be repeated after the RagBot process restarts or the browser reloads. This preserves the existing V1 authentication semantics.

## System

- `GET /system/database-status`
- `POST /system/database-initialize`
- `GET /system/capabilities`
- `GET /datasources`

Initialization body is fixed to `{"confirmation":"CREATE_EVALUATION_TABLES"}` and is additionally gated by `EVAL_ALLOW_DB_INIT`.

## Datasets

- `POST /datasets/import`: multipart `file` plus `dataset_type=PIPELINE_INSPECTION|STABILITY`.
- `GET /datasets`
- `GET /datasets/{dataset_id}`
- `GET /datasets/{dataset_id}/sessions`
- `GET /datasets/sessions/{dataset_session_id}/turns`
- `DELETE /datasets/{dataset_id}`

CSV/XLSX uploads require `query`; `session_id` and `time` are optional. Responses include counts, SHA256, issues/warnings, normalized sessions, and source lineage. The original binary is discarded and is never sent to MinIO.

## Runs

- `POST /runs`
- `GET /runs`
- `GET /runs/{run_id}`
- `DELETE /runs/{run_id}` (terminal only)
- `POST /runs/{run_id}/cancel`
- `GET /runs/{run_id}/sessions`
- `GET /run-sessions/{run_session_id}`
- `GET /run-turns/{run_turn_id}/trace`
- `GET /runs/{run_id}/events`

Run creation body:

```json
{
  "dataset_id": "uuid",
  "run_type": "DATASET_INSPECTION",
  "repeat_count": 1,
  "documents": ["General_FAQ"]
}
```

Stability run types require at least two repetitions. `STABILITY_QUERY` requires exactly one one-turn logical session, `STABILITY_SESSION` exactly one logical session, and `STABILITY_DATASET` one or more logical sessions. Dataset inspection requires one repetition. A dataset with no valid sessions cannot be run.

## Manual stability

- `POST /stability/manual`

```json
{
  "queries": [
    "افتتاح حساب چطور انجام می‌شود؟",
    "مدارکش چی هست؟",
    "چقدر طول میکشه؟"
  ],
  "repeat_count": 3,
  "documents": ["General_FAQ"]
}
```

The API creates one manual dataset session. Assistant messages are generated by the canonical pipeline and become history for later turns. One query selects `STABILITY_QUERY`; multiple queries select `STABILITY_SESSION`.

## SSE contract

`GET /runs/{run_id}/events` returns `text/event-stream` and supports `Last-Event-ID`. The frontend uses same-origin streaming `fetch`.

Events are `snapshot`, `run_started`, `session_started`, `turn_started`, `stage_completed`, `turn_completed`, `session_completed`, `progress`, `run_completed`, `run_cancelled`, and `run_failed`. Payloads contain only opaque evaluation IDs, status, stage name, counters, durations, and allowlisted safe error codes. Query/prompt/context/chunk/answer content never enters Redis. A disconnect stops only that stream; it does not cancel the run. Terminal snapshots/events close the stream. REST/PostgreSQL remains final truth.

If Celery enqueueing fails, the already-created PostgreSQL run is moved to `FAILED` with `EVALUATION_QUEUE_UNAVAILABLE`; it is not left indefinitely pending.

When `EVAL_USE_CELERY=false`, run creation and SSE return `EVALUATION_BACKGROUND_EXECUTION_UNAVAILABLE`. No in-process queue fallback is started.

## Frontend consumption contract

- Gate the application on `database-status`.
- Use the same dataset import endpoint from both panels.
- Build session rows from `/runs/{id}/sessions`.
- Expand turns with `/run-sessions/{id}`.
- Fetch full stage artifacts lazily from `/run-turns/{id}/trace`.
- Treat SSE as progress/invalidation, then refetch REST state.
- Display successful hash/text differences as `Divergence`, not `Error`.
- Never render prompt/context content as HTML.
